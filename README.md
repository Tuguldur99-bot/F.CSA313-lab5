# Lab05 - API систем тест: Postman ба Newman

Нэр: Ц.Төгөлдөр Оюутны код: B232270050

## Хувилбарууд

```
$ node -v
v23.11.0

$ newman -v
6.2.3
```

Хэрэгсэл: Postman (collection бүтээж, GUI-аар шалгасан), Newman (командын мөрөөс автоматаар ажиллуулсан).

## Тухай

Лекц 5-ын тест дизайны 5 алхмыг (бие даан тестлэгдэх функц → сонголтууд → төлөөлөх утгууд → спецификаци → бодит тест кейс) "хичээлд бүртгүүлэх" REST API (`server.js`) дээр хэрэгжүүлсэн. Тестлэгдэх функц нь `POST /registrations`. Тест бүр өөрт хэрэгтэй setup-аа (`PUT /students/:id`, `PUT /courses/:id`) өөрөө хийдэг (T09, T12 нь байхгүй оюутан/хичээл эсвэл буруу JSON шалгадаг тул setup шаардахгүй), өөрийн давтагдашгүй ID-тай (`S_T01`, `C_T01` гэх мэт) тул тестүүд бие даасан бөгөөд давтан ажиллуулахад аюулгүй.

## Ажиллуулах заавар

```bash
node server.js                                   # терминал 1: API (http://localhost:3000)

mkdir -p results                                 # терминал 2
newman run lab05-collection.json 2>&1 | tee results/newman-pass.txt
echo "exit=${PIPESTATUS[0]}" | tee -a results/newman-pass.txt
```

`| tee`-ийн дараа `$?` нь tee-ийн 0-ийг өгдөг тул exit code-ыг `${PIPESTATUS[0]}`-оор авсан.

## Тест дизайн: сонголт ба төлөөлөх утгууд

| Сонголт | Анги | Төлөөлөх утга |
|---|---|---|
| Оюутан | идэвхтэй, үзсэн хичээлтэй | `S_T01`, status `active`, coursesTaken `["CS201"]` |
| Оюутан | идэвхгүй | `S_T05`, status `inactive` |
| Оюутан | байхгүй | `S_T04_GHOST` (хэзээ ч үүсгээгүй) |
| Хичээл | байгаа | `C_T01` гэх мэт (PUT-аар үүсгэсэн) |
| Хичээл | байхгүй | `C_T06_GHOST` (хэзээ ч үүсгээгүй) |
| Урьдач нөхцөл ба үзсэн хичээл | урьдач нөхцөлгүй | prerequisites `[]` |
| Урьдач нөхцөл ба үзсэн хичээл | бүгдийг нь үзсэн | prerequisites `["CS201"]`, coursesTaken `["CS201"]` |
| Урьдач нөхцөл ба үзсэн хичээл | огт үзээгүй | prerequisites `["CS201"]`, coursesTaken `[]` |
| Урьдач нөхцөл ба үзсэн хичээл | зарим нь | prerequisites `["CS201","CS202"]`, coursesTaken `["CS201"]` |
| Хүсэлтийн формат | зөв / талбар дутуу / буруу JSON | `{studentID, courseID}` / `{studentID}` / `{"studentID": "S_T12", "courseID": ` |

**Боломжгүй хослолууд.** Оюутан байхгүй бол "оюутны үзсэн хичээл" гэсэн сонголт утгаа алддаг; хичээл байхгүй бол "хичээлийн урьдач нөхцөл" гэсэн сонголт утгаа алддаг. Иймд эдгээр сонголтын хослолыг (жишээ нь байхгүй оюутан + урьдач дутуу) тусад нь тест болгох боломжгүй — сервер тэр үед урьдач нөхцөл хүртэл ирдэггүй.

## Спецификацийн хүснэгт (12 спецификаци)

| № | Тохиолдол | Хүлээгдэх статус | Хүлээгдэх бие |
|---|---|---|---|
| T01 | Happy path: идэвхтэй оюутан, урьдач хангасан | 201 | `result=OK`, `registrationID` тоо |
| T02 | Хязгаар: урьдач нөхцөлгүй хичээл | 201 | `result=OK` |
| T03 | Хязгаар: хоосон `coursesTaken`, урьдачгүй хичээл | 201 | `result=OK` |
| T04 | Оюутан байхгүй | 200 | `ERROR_NO_STUDENT` |
| T05 | Идэвхгүй оюутан | 200 | `ERROR_INACTIVE_STUDENT` |
| T06 | Хичээл байхгүй | 200 | `ERROR_NO_COURSE` |
| T07 | Урьдач огт үзээгүй | 200 | `ERROR_PREREQUISITES`, `missing=["CS201"]` |
| T08 | Урьдачийн зарим нь дутуу | 200 | `ERROR_PREREQUISITES`, `missing=["CS202"]` |
| T09 | Давхар алдаа: оюутан байхгүй + хичээл байхгүй | 200 | `ERROR_NO_STUDENT` |
| T10 | Давхар алдаа: идэвхгүй оюутан + урьдач дутуу | 200 | `ERROR_INACTIVE_STUDENT` |
| T11 | `courseID` талбар дутуу | 400 | `ERROR_BAD_REQUEST` |
| T12 | Буруу JSON | 400 | `ERROR_BAD_JSON` |

Давхар алдааны (T09, T10) тохиолдолд аль алдаа буцахыг даалгаврын заавар заагаагүй. Эхлээд `server.js`-ийн шалгалтын дарааллаас (оюутан байхгүй → идэвхгүй → хичээл байхгүй → урьдач дутуу) таамаглаад, дараа нь `newman-pass.txt` дээр бодитоор батлав: байхгүй оюутан + байхгүй хичээл үед `ERROR_NO_STUDENT`, идэвхгүй оюутан + урьдач дутуу үед `ERROR_INACTIVE_STUDENT` буцсан. Өөрөөр хэлбэл оюутны шалгалт хичээлийнхээс түрүүлж, идэвхгүй байдлын шалгалт урьдач нөхцлийнхөөс түрүүлж ажилладаг.

## Collection-ы бүтэц

Collection нь 12 folder (T01–T12) агуулна. Folder бүр өөрийн setup PUT хүсэлт(үүд) + `POST /registrations` + oracle-уудтай. `registrationID`-ийн яг утгыг шалгаагүй, зөвхөн тоо мөн эсэхийг шалгасан (сервер ажиллах хугацаанд ID хуримтлагддаг тул).

Assertion-ы задаргаа (`results/newman-pass.txt`-тэй тулгаж болно):
- Setup PUT-ийн assertion: 17 (T01:2, T02:2, T03:2, T04:1, T05:2, T06:1, T07:2, T08:2, T09:0, T10:2, T11:1, T12:0)
- POST-ийн assertion: 27 (статус + result, T01 дээр `registrationID` тоо, T07/T08 дээр `missing`)
- Нийт: 17 + 27 = **44 assertion**, 29 хүсэлт (17 setup + 12 POST)

## Үр дүн

| Ажиллуулалт | Файл | Requests failed | **Assertions executed / failed** | Exit code |
|---|---|---|---|---|
| PASS | `results/newman-pass.txt` | 0 / 29 | **44 / 0** | **0** |
| FAIL | `results/newman-fail.txt` | 0 / 29 | **44 / 1** | **1** |
| DOWN | `results/newman-down.txt` | 29 / 29 | **44 / 44** | **1** |

README-д бичсэн тестийн тоо (44 assertion) нь `results/newman-pass.txt`-ийн төгсгөлийн хүснэгтийн `assertions executed` тоотой яг таарна.

**PASS.** 12 спецификаци бүгд амжилттай: `assertions 44 executed, 0 failed`, `exit=0`.

**FAIL.** `lab05-collection-fail.json` дотор T01-ийн oracle-ыг зориуд буруу болгосон (амжилттай бүртгэлд 201 биш 200 хүлээх). Үр дүн: яг 1 assertion унасан — `Амжилттай бүртгэл: статус 200 — expected response to have status code 200 but got 201`, `exit=1`. Үндсэн `lab05-collection.json` зөв хэвээр үлдсэн. Энэ бол CI quality gate-ийн зарчим: нэг oracle зөрвөл exit code 0 биш болж, pipeline зогсоно.

**DOWN.** Серверийг унтраагаад (Ctrl+C) үндсэн collection-ыг ажиллуулахад бүх хүсэлт `connect ECONNREFUSED 127.0.0.1:3000` алдаатай (`requests 29 failed`), `exit=1`.

**Интерфейсийн алдаа ба oracle-ийн алдааны ялгаа.** DOWN үед 44 assertion бүгд "унасан" гэж харагдах ч сервер 44 буруу хариу өгөөгүй — хариу огт ирээгүй тул assertion-д уншуулах зүйл байгаагүй (`"undefined" is not valid JSON`); үндсэн шалтгаан нь 29 хүсэлтийн холболтын алдаа (интерфейсийн алдаа). Харин FAIL үед сервер хариу өгсөн, харин хариу нь бидний oracle-той зөрсөн (oracle-ийн алдаа), тэр нь зөвхөн 1 assertion унагаав.

## Дүгнэлт

Дизайны 5 алхмаас хамгийн их бодол шаардсан нь сонголтуудыг тодорхойлж, тэдгээрийн утгыг эквивалент ангид хуваах алхам байсан, учир нь хүснэгтийн бүх хослолыг тест болгох боломжгүй (боломжгүй хослолууд таарсан). Жишээ нь оюутан байхгүй үед "оюутны үзсэн хичээл" гэсэн сонголт утгаа алддаг, хичээл байхгүй үед "урьдач нөхцөл" утгаа алддаг тул эдгээр хослолыг хасч, оронд нь ач холбогдолтой давхар алдааны хослолуудыг (T09, T10) сонгосон. Заавар нь давхар алдааны үед аль алдаа буцахыг заагаагүй байсан тул `server.js`-ийн шалгалтын дарааллаас таамаглаад, тестээр бодитоор баталсан. Тест бүрийг бие даасан байлгахын тулд тест бүр өөрийн давтагдашгүй ID-тай оюутан, хичээлийг өөрөө PUT-аар үүсгэдэг болгосон, тиймээс collection-ыг дахин дахин ажиллуулахад үр дүн өөрчлөгдөхгүй. `registrationID` хуримтлагддаг тул яг утгыг нь шалгалгүй зөвхөн тоо мөн эсэхийг шалгасан. Миний тестүүд `server.js`-аас ямар нэг согог олоогүй: 12 спецификаци бүгд эхний ажиллуулалтаар давсан. Гэхдээ энэ нь тестүүд хэрэггүй гэсэн үг биш, учир нь FAIL ажиллуулалт нэг oracle-ыг буруу болгоход тест үнэхээр унаж, exit code 1 өгч байгааг харуулсан, өөрөөр хэлбэл тестүүд согог олох чадвартай. DOWN ба FAIL ажиллуулалтыг харьцуулснаар интерфейсийн алдаа (DOWN: хариу огт ирээгүй, 29 хүсэлт унасан) ба oracle-ийн алдаа (FAIL: хариу ирсэн ч хүлээлттэй зөрсөн, 1 assertion унасан) хоёрыг ялгах нь чухал гэдгийг ойлгосон. Нэг сонирхолтой ажиглалт бол сервер бизнесийн алдаануудыг (оюутан байхгүй, урьдач дутуу) 200 статусаар, зөвхөн хүсэлтийн форматын алдааг 400-аар буцаадаг — энэ нь Лекц 5-ын семантик боловч тестэнд статус код ба result-ийг хоёуланг нь шалгах шаардлагатай болгосон. Цаашид давхар алдааны шалгалтын дарааллыг заавал баримт бичигт тусгах хэрэгтэй гэж үзэж байна, учир нь үүнгүй бол хоёр хэрэгжүүлэлт өөр өөр алдаа буцааж болно.
